# Analysis Module Contracts v2

Analysis modules consume the normalized `data_pack.json` fields and return structured findings. They must not call MCP tools directly; data access happens before analysis.

## Common Input

```json
{
  "task_id": "",
  "module": "amazon_competitor",
  "method_ids": ["competitor.price_value_matrix", "competitor.review_gap"],
  "data_pack_path": "reports/task/data/data_pack.json",
  "allowed_entities": ["products", "reviews", "keywords"],
  "question": "What competitor weaknesses create an opportunity?",
  "output_path": "reports/task/analysis/competitors.json"
}
```

Before any module runs, `data_pack.json` must have:

- `normalization.deduped = true`
- stable `before_counts`, `after_counts`, `removed_counts`, and `cross_validated_counts`
- at least 1000 deduped keyword rows for standard/deep reports
- keyword Chinese mapping fields: `keyword_cn`, `intent_cn`, `relevance_cn`
- product Chinese mapping fields: `title_cn`, `segment_cn`, `positioning_cn`
- `source_ids` and `validation` on deduped entities where cross-source evidence exists

`title_cn`, `segment_cn`, and `positioning_cn` are normalized evidence fields, not the final customer-facing label contract. Customer-facing product names, segment names, keyword tags, and lifecycle type names must be generated by the analysis layer in `analysis_plan.report_label_profile`.

## Common Output

```json
{
  "module": "amazon_competitor",
  "method_ids": [],
  "status": "complete | partial | blocked",
  "used_source_ids": ["src_001"],
  "findings": [],
  "tables": [],
  "charts": [],
  "evidence": [],
  "confidence": "high | medium | low",
  "limitations": []
}
```

Every module output must include `used_source_ids`. If a module is blocked or partial, it must include a limitation and the missing evidence.

Module outputs should also expose report-ready blocks for the v2 HTML bundle:

- `kpis`: short label/value/subtext cards.
- `tables`: evidence rows with source IDs for audit artifacts. Customer HTML must replace source IDs with client-readable evidence scope labels.
- `cards`: opportunities, VOC clusters, risks, or competitor layers.
- `charts`: simple series that can be rendered as CSS/SVG or kept as tables offline.
- `html_report_hint`: one of `market_depth`, `lifecycle_strategy`, or `demand_gap`.
- `html_section_hint`: the target section id from `html-report-design-contract.md`.

## Guardrails

- Do not treat Sorftime monthly sales estimates as official Amazon sales.
- Do not treat TikTok sold counts or video engagement as Amazon purchase validation.
- Do not write precise percentages from small review samples.
- Do not recommend an opportunity supported by only one weak source unless labeled speculative.
- Do not rank keyword opportunities until high-relevance terms are separated from adjacent/noisy category terms and ASIN traffic terms.
- Do not write a P&L without landed cost, FBA fees, return rate, referral fee, and ad cost. Use threshold models instead.
- Do not invent lifecycle SKU economics when supply evidence is missing; use directional price bands and mark the gap.
- Do not treat demand-gap findings as proven demand unless tied to reviews, keywords, or multiple public sources.

`analysis_plan.json` must contain:

```json
{
  "task_id": "",
  "research_object": "",
  "primary_purpose": "",
  "secondary_purposes": [],
  "method_chain": [
    {
      "method_id": "market.top100_competitor_scan",

  ],
  "report_label_profile": {

    "product_title_labels": {
      "B0EXAMPLE": "customer-facing Chinese product short name"
```

The validator requires `method_chain`, `confidence`, and `limitations`. Production customer reports should also include `report_label_profile`; if it is missing, renderers may only use neutral diagnostics or data-derived labels and must not hard-code category-specific labels.

## Report Readiness View

Every rendered HTML bundle must include one unified `report_readiness_view` derived from data readiness, critic state, validator state, and `delivery_result.json`. All four HTML pages read this view instead of independently interpreting partial data.

```json
{
  "status": "完整可交付 | 诊断交付 | 阻断交付",
  "decision": "Go | Watch | No-Go",
  "evidence_strength": "高 | 中 / 诊断交付 | 低 / 阻断交付",
  "supply_blocked": true,
  "supply_status": "供应链测算未达门槛",
  "blocking_gaps": [
    {
      "module": "supply_chain",
      "reason": "valid_supplier_quotes below 50 or field quality failed",
      "impact": "profit and landed-cost conclusions blocked",
      "next_action": "rerun Sorftime 1688 with alternate searchName seeds and page depth"
    }
  ]
}
```

If `supply_blocked=true`, customer HTML may still render market/VOC/lifecycle strategy modules, but it must not render profit/margin conclusions or phrases equivalent to `供应链可控度较高`, `50+ 可打样`, or `毛利率可测算`.

## Optional Module Artifact Shapes

`analysis/cosmo_alexa_tags.json` is required for complete customer HTML:

```json
{
  "module": "cosmo_alexa_tags",
  "schema_version": "2026-06-11.cosmo-alexa-tags.v1",
  "basis": {
    "effective_products": 0,
    "effective_keywords": 0,
    "effective_reviews": 0,
    "tiktok_signals": 0,
    "supplier_records": 0
  },
  "coverage_summary": {
    "relation_total": 15,
    "covered_relations": 15,
    "low_confidence_relations": 0,
    "evidence_records": 0
  },
  "relations": [
    {
      "relation_type": "USED_FOR_FUNC",
      "label_cn": "功能用途",
      "tag_terms": ["customer-facing term"],
      "evidence_sources": ["effective_products", "effective_keywords"],
      "confidence": 0.75,
      "evidence_count": 12,
      "listing_action": "Listing action",
      "qa_action": "QA action",
      "ad_action": "Advertising action"
    }
  ],
  "limitations": []
}
```

The `relations` array must contain exactly these 15 relation types: `USED_FOR_FUNC`, `USED_FOR_EVE`, `USED_FOR_AUD`, `CAPABLE_OF`, `USED_TO`, `USED_AS`, `IS_A`, `USED_ON`, `USED_IN_LOC`, `USED_IN_BODY`, `USED_WITH`, `USED_BY`, `xINTERSTED_IN`, `xIs_A`, and `xWANT`. Tags must be extracted from current effective evidence only or from `analysis_plan.report_label_profile.cosmo_relation_terms`, which is the AI-analyzed category label profile for the current research object. Hard-coded category vocabulary is invalid. AI profile terms are candidates, not facts: each customer-visible term must be supported by current effective data text at the term level. Category-specific labels are allowed only when current evidence supports that category context; for example, generic `outdoor`, `box`, or `waterproof` evidence must not create hunting-specific labels for unrelated products. If the AI label profile provides a term but the current effective data text does not provide enough supporting matches, keep it out of customer-visible `terms` and use the relation slot as a low-coverage diagnostic instead of promoting it to high confidence.

COSMO tags must be relation-specific. A complete 15-card matrix is invalid if many cards reuse the same term set or if one generic term is repeated across too many high/medium-confidence relations. English cue matching must use word boundaries for short tokens, so `pet` cannot match `competitor` and `cat` cannot match unrelated word fragments.

The market-depth renderer must display this artifact as four zones: a 15-relation matrix, a high-confidence tag ranking, a product/user label gap panel, and Listing / QA / ad action cards. The matrix itself must be split into two visible lanes, `产品标签 · 产品被算法识别为什么` and `用户标签 · 用户为什么搜索/购买`, so product identity signals and user intent signals are not mixed in one generic card grid. Matrix cells must show customer-readable `产品意图/用户意图` labels and `产品/用户` markers while keeping relation type keys and compact P/U slot IDs internal. Relations with little or no evidence remain visible as low-coverage diagnostics; they must not be promoted to high confidence to keep the visual grid full. Customer-visible text must not expose internal relation codes such as `USED_FOR_FUNC`, `CAPABLE_OF`, `xWANT`, synthetic placeholders such as `REL_1`, or compact slot IDs such as `P01/U09`.

```json
      "ecosystem_segment": "scenario or subsegment",
      "priority": 88,
      "reference_asin": "B0EXAMPLE",
      "reference_competitor": "reference competitor label",
      "reference_price": 29.99,
      "reference_rating": 4.5,
      "reference_reviews": 1200,
      "reference_sales": 300,
      "supplier_title": "matched 1688 title or diagnostic",
      "pain": "VOC or demand reason"
    }
  ],
  "recommended_skus": [],
  "ecosystem_nodes": [],
  "skus": [],
  "bundles": [],
  "roadmap": [],
  "risks": [],
  "filter_diagnostics": {
    "effective_products": 0,
```

`sku_candidate_pool` is the full analysis pool and should target 30-80 candidates when evidence is available. `recommended_skus` is only the top recommendation set. The five fixed SKU cards in HTML are display slots, not the full pool. If this file is absent or the pool is not decision-grade, render the full template in diagnostic mode instead of generating old fallback SKUs.
